1. Постановка задачи
К приложению добавляются регистрация, вход, выход и три роли с различающимся набором доступных функций. Незалогиненный пользователь не должен попадать на внутренние экраны ни по кнопке, ни вводом адреса вручную.
1.1. Соответствие конструкций
1.2. Главное отличие от Spring
В Spring проверка прав выполнялась на сервере, и обойти её из браузера было невозможно. Здесь весь код приложения загружен в браузер пользователя и полностью ему доступен. Любую клиентскую проверку можно обойти правкой значений в DevTools.
Отсюда правило, вокруг которого построена вся работа:
Клиентская проверка прав — это удобство интерфейса. Она скрывает от пользователя то, что ему всё равно не разрешат сделать, и избавляет от бессмысленных запросов. Настоящая защита находится только на сервере.
Практическая проверка этого утверждения входит в задание на оценку «5».
Отдельно: пароль на клиенте не хешируется. Хеширование выполняет сервер. Клиент передаёт пароль как есть — по защищённому соединению. Хеширование на клиенте не даёт ничего: полученный хеш просто становится новым паролем, и перехватившему его достаточно отправить именно хеш.
2. Ход выполнения
2.1. Хранение сессии
Токен доступа живёт недолго (по умолчанию 15 минут), токен обновления — неделю. Оба нужно пережить перезагрузку страницы, поэтому они кладутся в shared_preferences, то есть в localStorage.
// lib/state/auth_notifier.dart

class AuthNotifier extends ChangeNotifier {
  static const _kAccess = 'auth_access_token';
  static const _kRefresh = 'auth_refresh_token';

  final SharedPreferences _prefs;
  final AuthApi _api;

  AuthNotifier(this._prefs, this._api);

  AppUser? _user;
  String? _accessToken;

  AppUser? get user => _user;
  String? get accessToken => _accessToken;
  bool get isAuthenticated => _user != null;

  bool has(Role role) => _user != null && _user!.role.level >= role.level;

  /// Восстановление сессии при запуске приложения.
  /// Вызывается один раз до построения дерева виджетов.
  Future<void> restore() async {
    final access = _prefs.getString(_kAccess);
    final refresh = _prefs.getString(_kRefresh);
    if (access == null) return;

    _accessToken = access;
    try {
      _user = await _api.me();          // токен ещё жив
    } on UnauthorizedException {
      if (refresh != null) {
        try {
          await _refreshWith(refresh);   // токен истёк, обновляем
        } catch (_) {
          await logout();
        }
      } else {
        await logout();
      }
    } catch (_) {
      // Сервер недоступен: сессию не сбрасываем, покажем ошибку позже
    }
    notifyListeners();
  }

  Future<void> login(String username, String password) async {
    final result = await _api.login(username, password);
    _accessToken = result.accessToken;
    _user = result.user;
    await _prefs.setString(_kAccess, result.accessToken);
    await _prefs.setString(_kRefresh, result.refreshToken);
    notifyListeners();
  }

  Future<void> logout() async {
    _user = null;
    _accessToken = null;
    await _prefs.remove(_kAccess);
    await _prefs.remove(_kRefresh);
    notifyListeners();
  }
}
Что именно допустимо класть в localStorage:
Роль можно хранить для того, чтобы нарисовать интерфейс. Но решение «разрешить операцию» принимает сервер, который берёт роль из подписанного токена, а не из того, что прислал клиент.
2.2. Защита маршрутов
go_router вызывает redirect перед каждым переходом. Возврат null означает «переход разрешён», возврат строки — «отправить на этот адрес».
// lib/router.dart

GoRouter buildRouter(AuthNotifier auth) {
  return GoRouter(
    // Маршрутизатор пересчитает redirect при каждом notifyListeners()
    refreshListenable: auth,
    initialLocation: '/',
    redirect: (context, state) {
      final loggedIn = auth.isAuthenticated;
      final target = state.matchedLocation;
      final isPublic = target == '/login' || target == '/register';

      // Не вошёл и идёт на закрытый экран — на вход,
      // запомнив адрес, куда он хотел попасть
      if (!loggedIn && !isPublic) {
        return '/login?from=${Uri.encodeComponent(state.uri.toString())}';
      }

      // Уже вошёл и идёт на экран входа — на главную
      if (loggedIn && isPublic) return '/';

      return null;
    },
    routes: [
      GoRoute(path: '/login', builder: (c, s) => const LoginScreen()),
      GoRoute(path: '/register', builder: (c, s) => const RegisterScreen()),
      GoRoute(path: '/', builder: (c, s) => const DashboardScreen()),

      GoRoute(
        path: '/books',
        builder: (c, s) => const BookListScreen(),
        // Проверка на уровне отдельной ветки маршрутов
        redirect: (context, state) =>
            auth.has(Role.librarian) ? null : '/forbidden',
        routes: [
          GoRoute(path: 'new', builder: (c, s) => const BookFormScreen()),
        ],
      ),

      GoRoute(
        path: '/admin/users',
        builder: (c, s) => const UsersScreen(),
        redirect: (context, state) => auth.has(Role.admin) ? null : '/forbidden',
      ),

      GoRoute(path: '/forbidden', builder: (c, s) => const ForbiddenScreen()),
    ],
    errorBuilder: (c, s) => NotFoundScreen(location: s.uri.toString()),
  );
}
Параметр from нужен, чтобы после успешного входа вернуть пользователя туда, куда он шёл, а не на главную. Это заметная деталь удобства: человек открыл присланную ссылку на карточку книги, его отправили на вход, и после входа он должен попасть на ту самую карточку.
2.3. Скрытие недоступных элементов
Кнопку, которой пользователь всё равно не сможет воспользоваться, показывать не нужно:
if (context.watch<AuthNotifier>().has(Role.librarian))
  FilledButton.icon(
    onPressed: () => context.go('/books/new'),
    icon: const Icon(Icons.add),
    label: const Text('Добавить книгу'),
  ),
Повторим: это не защита, а уборка интерфейса. Пользователь, который откроет /books/new вручную, будет остановлен проверкой в redirect, а если обойдёт и её — получит с сервера код 403.
2.4. Обработка истёкшего токена
Токен может истечь прямо во время работы. Правильное поведение: молча обновить его и повторить запрос, а если обновление не удалось — вывести пользователя из системы.
onError: (error, handler) async {
  final status = error.response?.statusCode;

  if (status == 401 && !error.requestOptions.path.contains('/auth/')) {
    try {
      await authNotifier.refreshTokens();
      // Повторяем исходный запрос с новым токеном
      final options = error.requestOptions;
      options.headers['Authorization'] = 'Bearer ${authNotifier.accessToken}';
      final response = await Dio().fetch(options);
      return handler.resolve(response);
    } catch (_) {
      await authNotifier.logout();
    }
  }
  return handler.reject(error);
}
Условие !path.contains('/auth/') обязательно: без него неудачная попытка входа с кодом 401 вызовет попытку обновления токена, та тоже вернёт 401, и получится бесконечный цикл.
Для проверки запустите сервер с коротким сроком жизни токена:
node mock-server.js --ttl 60
2.5. Выход по неактивности
Таймер сбрасывается при любом действии пользователя. Отслеживать удобно на уровне всего приложения:
import 'dart:async';                      // Timer
import 'package:flutter/services.dart';   // HardwareKeyboard, KeyEvent

class InactivityWatcher extends StatefulWidget {
  final Duration timeout;
  final VoidCallback onTimeout;
  final Widget child;

  const InactivityWatcher({
    super.key,
    required this.timeout,
    required this.onTimeout,
    required this.child,
  });

  @override
  State<InactivityWatcher> createState() => _InactivityWatcherState();
}

class _InactivityWatcherState extends State<InactivityWatcher> {
  Timer? _timer;

  @override
  void initState() {
    super.initState();
    // Клавиатуру слушаем глобально. Виджет KeyboardListener здесь не подошёл бы:
    // он сообщает о нажатиях, только когда его FocusNode в фокусе, а у обёртки
    // над всем приложением фокуса нет — набор текста в форме не сбрасывал бы
    // таймер, и пользователя выбросило бы прямо посреди заполнения.
    HardwareKeyboard.instance.addHandler(_onKey);
    _restart();
  }

  // false означает «событие не обработано, передайте его дальше».
  bool _onKey(KeyEvent event) {
    _restart();
    return false;
  }

  void _restart() {
    _timer?.cancel();
    _timer = Timer(widget.timeout, widget.onTimeout);
  }

  @override
  void dispose() {
    HardwareKeyboard.instance.removeHandler(_onKey);
    _timer?.cancel();
    super.dispose();
  }

  @override
  Widget build(BuildContext context) {
    return Listener(
      // Перехват без поглощения: событие идёт дальше к виджетам.
      behavior: HitTestBehavior.translucent,
      onPointerDown: (_) => _restart(),
      onPointerMove: (_) => _restart(),
      onPointerSignal: (_) => _restart(),
      child: widget.child,
    );
  }
}
Учтите: таймер живёт в памяти вкладки. При перезагрузке страницы он обнулится. Чтобы неактивность отслеживалась и через перезагрузку, время последнего действия нужно записывать в localStorage и сверять при запуске.

Дополнительно:
Реализована усиленная проверка пароля при регистрации: длина не менее восьми символов, наличие цифры, наличие специального символа. Проверка выполняется по мере ввода, а не только по нажатию кнопки.
Реализованы три роли с различающимся набором функций, а не с разным объёмом одного и того же:

библиотекарь — управление книгами и справочниками, оформление и закрытие выдач, работа с читателями;
администратор — управление пользователями и ролями, физическое удаление, восстановление записей, просмотр статистики. У каждой роли должен быть хотя бы один экран, недоступный остальным.
Маршруты защищены через redirect. Попытка открыть чужой адрес вручную приводит на экран отказа, а не на пустой экран и не к падению.
Элементы интерфейса, недоступные текущей роли, скрыты.
После входа пользователь возвращается на тот адрес, с которого его перенаправили на форму входа.
Ответ сервера с кодом 403 обрабатывается и показывается понятным сообщением.
На оценку «5»
Дополнительно:
Реализовано автоматическое обновление токена: при получении кода 401 приложение обновляет токен и повторяет запрос прозрачно для пользователя. Проверяется запуском сервера с параметром --ttl 60.
Реализован выход по неактивности: после трёх минут без действий пользователя сессия завершается с предупреждением за 30 секунд до этого.
Реализовано ограничение общей длительности сессии: через заданное время пользователь выходит независимо от активности.
Неудачное обновление токена приводит к корректному выходу без зацикливания запросов. Продемонстрируйте, что бесконечного цикла не возникает.
